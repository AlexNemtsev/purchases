# «Учёт закупок» — разбивка на задачи по ТЗ v3 (FSD + SvelteKit)

Источник истины — `purchase-tracker-spec-v3.md` (далее «ТЗ»). Номера
разделов и тест-кейсов относятся к нему. Эта версия заменяет предыдущие.

## Правила для исполнителя (ИИ-агента)

- Одна задача = один законченный PR/коммит. Не начинать задачу, пока не
  закрыты её зависимости.
- Не менять ТЗ. Если в нём противоречие или дыра — остановиться и спросить.
- Перед началом проверить, что уже есть в репозитории (слои, SvelteKit,
  PWA, shadcn-svelte, страница «Разное»), и не дублировать. Если в проекте
  уже есть свои договорённости по FSD, они приоритетнее схемы ниже.
- Деньги — копейки (`number`), проценты — промилле, расчёты внутри —
  `BigInt`. Чистая логика не импортирует Svelte, `window`, `localStorage`.
- Каждая задача заканчивается: `vitest`, `svelte-check`, линтер и проверка
  границ FSD без ошибок; в описании PR перечислены закрытые тест-кейсы
  из ТЗ §17.
- Тесты лежат рядом с кодом (`*.test.ts` в том же сегменте).

## Правила FSD для проекта

- Слои (сверху вниз): `app` → `routes` (страницы SvelteKit) → `widgets` →
  `features` → `entities` → `shared`. Отдельного слоя `pages` нет: роль
  страниц играют маршруты `src/routes/**`.
- Импорт только из слоёв ниже. Слайсы одного слоя не импортируют друг
  друга; исключение — `entities`, через явный публичный API `@x`
  (например, `entities/receipt/@x/purchase.ts`).
- Каждый слайс экспортирует наружу только `index.ts`.
- Сегменты: `ui`, `model` (типы, состояние, бизнес-логика), `lib`, `api`,
  `config`.
- **Сущности укрупнены:** вся логика сущности лежит в её слайсе — тип,
  расчёты, валидация, сводки, состояние (стор), каскады удаления,
  презентационный UI. Отдельных «общих» слайсов вроде `discount` или
  `ledger` нет.
- Маршруты в `src/routes` собирают страницу из виджетов и фич, своей
  бизнес-логики не содержат.
- Алиасы слоёв (`@app`, `@widgets`, `@features`, `@entities`, `@shared`)
  задаются в `kit.alias`; проверить, что они попали в
  `.svelte-kit/tsconfig.json` и в конфиг `vitest`.
- shadcn-svelte: в `components.json` алиас компонентов на `@shared/ui`.
- Линтер границ: `steiger` или `eslint-plugin-boundaries` с учётом того,
  что слоя `pages` нет; входит в CI.

## Целевая структура

```text
src/
├── app/                        # layout-компоненты, провайдеры, глобальные стили, PWA, ошибки хранилища
├── routes/                     # страницы SvelteKit (тонкие)
│   ├── +layout.svelte
│   ├── +page.svelte                        # список закупок
│   ├── purchases/[purchaseId]/+page.svelte # экран закупки
│   ├── categories/+page.svelte             # категории
│   └── misc/+page.svelte                   # «Разное» (уже существует)
├── widgets/
│   ├── purchase-list/
│   ├── purchase-header/        # сводка + переключатель представлений
│   ├── purchase-by-receipts/
│   ├── purchase-by-categories/
│   └── category-list/
├── features/
│   ├── edit-purchase/          # создать, правка названия/даты, удалить
│   ├── edit-receipt/           # форма чека, удалить
│   ├── edit-operation/         # форма операции, предупреждения, удалить
│   ├── manage-categories/      # создать, переименовать, архивировать, вернуть
│   └── export-json/
├── entities/
│   ├── operation/              # тип, скидка и итог, предупреждения, валидация, стор, каскад, OperationCard
│   ├── receipt/                # тип, скидка чека, эффективная доля, сводка, валидация, стор, каскад, ReceiptCard
│   ├── category/               # тип, валидация и уникальность, сводка, сортировка, стор, CategoryBadge
│   └── purchase/               # тип, автоназвание, сводка, сортировка, валидация, стор, каскадное удаление, PurchaseCard
└── shared/
    ├── config/                 # лимиты
    ├── lib/
    │   ├── money/              # roundDiv, разбор и форматирование денег и процентов
    │   ├── date/               # ISO-даты, dd.mm.yyyy, локальное «сегодня»
    │   └── discount/           # AmountDiscount | PercentDiscount, расчёт значения скидки, пределы
    ├── api/
    │   └── document-store/     # коллекции поверх одного JSON-документа в localStorage
    └── ui/                     # shadcn-svelte + MoneyInput, PermilleInput, AmountOrPercentInput, ConfirmDialog, WarningList, EmptyState
```

**Решения по раскладке** (можно менять, если не подходят):

- Зависимости между сущностями (через `@x`) идут в одну сторону, без
  циклов: `operation` ни от кого не зависит; `receipt` → `operation`;
  `purchase` → `receipt`, `operation`; `category` → `operation`, `receipt`.
- Итог операции считается от переданной доли скидки чека (дробь
  `{ numerator, denominator } | null`), поэтому `operation` не импортирует
  `receipt`. Доступность категории и прочие внешние данные передаются в
  функции аргументами.
- Скидка чека и скидка операции делят только арифметику суммы/процента:
  она вынесена в `shared/lib/discount` (универсальный код без знания о
  чеках и операциях), а не в отдельную сущность.
- Хранение: один JSON-документ (ТЗ §14), но у каждой сущности свой
  стор над своей «коллекцией» из `shared/api/document-store`.
  Каскадное удаление раскладывается по сущностям: `purchase` вызывает
  удаление в `receipt`, тот — в `operation` (внутри одной транзакции
  документа).
- Сводки по нескольким сущностям (`calculateReceiptSummary`,
  `calculatePurchaseSummary`, `calculateCategorySummary`) живут в той
  сущности, чьи итоги они считают; сборка двух представлений закупки —
  в виджетах.

### T1.4 `shared/api/document-store` (L)
Зависит от: T0.2. ТЗ: §14. Тесты: 37, 38.
- Интерфейс `Collection<T>` (асинхронные методы, реактивное чтение
  через подписку) и «транзакция» по нескольким коллекциям внутри одной
  записи документа — для каскадов.
- Реализации: in-memory (для тестов) и localStorage: ключ
  `purchase-tracker:data`, документ `{ schemaVersion: 1, purchases,

- Запасной генератор id при отсутствии `crypto.randomUUID`.
- Бизнес-типов не знает (дженерик); общий набор контрактных тестов
  запускается на обеих реализациях.

Готово: тесты на повреждённые данные, неизвестную версию,
`QuotaExceededError`, событие `storage`, транзакцию с откатом при ошибке.

## Этап 2. entities (вся логика сущности в её слайсе)

Для каждой сущности: типы, расчёты, валидация, стор (на runes Svelte 5 поверх
своей коллекции), каскады, презентационный UI (только пропсы), публичный API.

### T2.1 `entities/operation` (M)
Зависит от: T1.3, T1.4. ТЗ: §6, §12. Тесты: 9–17.
- `calculateOperationDiscount`; `calculateOperationNet(operation,
  receiptRate)` → `{ base, operationDiscount, receiptDiscount, net,
  warnings }`. Предупреждения: `net < 0`, `refund > expense`. Без
  автокоррекции.
- `validateOperation` (сумма > 0, возврат > 0 если указан, категория
  обязательна и активна для новой операции; при редактировании прежнюю
  архивную категорию можно сохранить, пока пользователь не выберет другую).
- Стор операций; `removeByReceipts(tx, receiptIds)`.
- `OperationCard` (категория, расход, возврат, итог, предупреждение,
  комментарий).
- Публичный API `@x` для `receipt`, `purchase`, `category`.

Готово: примеры ТЗ §6 (340 / 306 / 630 ₽, полный возврат = 0),
негативные кейсы с предупреждениями, независимое округление (№17).

### T2.2 `entities/receipt` (L)
Зависит от: T2.1. ТЗ: §4, §7, §11. Тесты: 1–8, 20–22.

Готово: примеры ТЗ §4 (750 / 725 ₽), скидка >100 %, `receiptAmount = 0`;

### T2.3 `entities/category` (M)
Зависит от: T2.1, T2.2. ТЗ: §7, §8. Тесты: 24, 30, 31, 32.

Готово: дубликаты не создаются и не получаются переименованием; итог
