# PWA «Учёт закупок» — техническая спецификация v3

## 1. Назначение

Мобильное offline-first PWA для локального учёта закупок с несколькими
чеками, категориями операций, скидками в несколько этапов и фактическими
возвратами от продавца.

- Frontend: SvelteKit (SPA-режим), Svelte 5, Vite, TypeScript, shadcn-svelte.
- PWA: `vite-plugin-pwa` (уже настроен).
- Хранение: **`localStorage`** на время отладки модели; после отладки данных
  планируется миграция на IndexedDB (см. разделы 14 и 15).
- Backend, аккаунты и синхронизация не нужны.
- Валюта одна (₽).
- Деньги хранятся целым числом копеек, проценты — целым числом промилле
  (10 ‰ = 1 %, 1 ‰ = 0,1 %).

Все вычисления скидок и итогов выносятся в чистые доменные функции
(раздел 16) и покрываются тестами (раздел 17). Расчёты не находятся в
Svelte-компонентах.

## 2. Доменная модель

```text
Purchase
└── Receipt[]
    └── Operation[]
        └── Category

Category — общий справочник, не принадлежит отдельной закупке.
```

- **Закупка (`Purchase`)** — логическая закупка с названием и датой.
- **Чек (`Receipt`)** — отдельный чек/заказ внутри закупки. Является
  *источником скидки* для своих операций: хранит введённую пользователем
  сумму до скидок и настройки скидки (1–2 части). Сам по себе **не** задаёт
  итоговые суммы закупки.
- **Операция (`Operation`)** — расходная позиция внутри чека. Связана с
  обязательной категорией; может содержать возврат и индивидуальную скидку.
- **Категория (`Category`)** — общий справочник, управляемый на отдельной
  странице. Название и необязательный комментарий. Категории архивируются и
  могут быть возвращены из архива.

Итоги закупки и категорий считаются **по операциям**. Чек даёт операциям
эффективный процент скидки и служит местом сверки с суммой операций.

## 3. Типы

```ts
// Деньги: целое число копеек. Проценты: целое число промилле (1 = 0,1 %).
type Kopecks = number
type Permille = number

// Один способ ввода — одно значение. Второе значение не хранится,
// а при необходимости вычисляется на лету для подсказки в UI.
type AmountDiscount = { mode: 'amount'; amountKopecks: Kopecks }
type PercentDiscount = { mode: 'percent'; permille: Permille }

type PercentBase = 'original' | 'afterPrevious'

// Часть скидки чека. Для процентной части хранится база.
// У первой части база всегда 'original' (в UI не показывается).
type ReceiptDiscountPart =
  | AmountDiscount
  | (PercentDiscount & { percentBase: PercentBase })

interface Purchase {
  id: string
  title: string
  date: string        // ISO-дата yyyy-mm-dd (локальная дата), без времени
  createdAt: string   // ISO-timestamp
  updatedAt: string
}

interface Receipt {
  id: string
  purchaseId: string
  amountKopecks: Kopecks  // сумма до скидок, вводится независимо от операций
  // 1 или 2 части. «Без скидки» = одна часть { mode: 'amount', amountKopecks: 0 }.
  discountParts: [ReceiptDiscountPart] | [ReceiptDiscountPart, ReceiptDiscountPart]
  comment: string
  createdAt: string
  updatedAt: string
}

interface Category {
  id: string
  title: string
  comment: string
  archived: boolean
  createdAt: string
  updatedAt: string
}

interface Operation {
  id: string
  receiptId: string
  categoryId: string
  amountKopecks: Kopecks        // расход до скидок и возвратов
  comment: string
  // Возврат в БРУТТО-шкале (в тех же единицах, что и расход, т.е. до скидок).
  // Отсутствие поля = возврата нет. Значение 0 не допускается.
  refundKopecks?: Kopecks
  // Отсутствие поля = индивидуальной скидки нет (скидка операции равна нулю).
  operationDiscount?: AmountDiscount | PercentDiscount
  createdAt: string
  updatedAt: string
}
```

`refundKopecks` вводится вручную. При включении возврата поле
предзаполняется суммой расхода, пользователь может изменить значение
(например, для частичного возврата). Возврат привязан к исходной расходной
операции; отдельного типа операции `refund` нет.

Идентификаторы: `crypto.randomUUID()`. Он доступен только в secure context
(HTTPS или `localhost`); при отладке с телефона по `http://<IP-в-LAN>`
нужен запасной генератор.

## 4. Скидки чека

Скидка чека состоит из одной или двух частей. Для каждой части пользователь
выбирает ввод: фиксированная сумма или процент.

- Первая часть применяется к исходной сумме чека.
- Вторая часть — сумма либо процент.
- Если вторая часть задана процентом, пользователь выбирает базу:
  - `original` — исходная сумма чека;
  - `afterPrevious` — сумма после первой скидки (скидки применяются
    последовательно).
- Фиксированная сумма вычитается как есть; база к ней не относится.
- Скидка может превышать 100 % суммы. Ограничения `discount <= amount` нет.
  Технический предел ввода процента — 1000,0 % (раздел 18, допущения).

Расчёт частей (все деления — целочисленные, округление — раздел 5):

```text
part0 = amount ? amountKopecks : roundDiv(gross * permille, 1000)
part1 = amount ? amountKopecks
      : percentBase == 'original'      ? roundDiv(gross * permille, 1000)
      : percentBase == 'afterPrevious' ? roundDiv((gross - part0) * permille, 1000)
receiptDiscountTotal = part0 + part1     (part1 = 0, если части нет)
```

Пример: чек 5 000 ₽, первая скидка 10 % = 500 ₽. Вторая 5 %:

- `original`: 250 ₽, общая скидка 750 ₽;
- `afterPrevious`: 225 ₽, общая скидка 725 ₽.

**Эффективный процент скидки чека** — точная дробь
`receiptDiscountTotal / receiptAmount`. В расчётах операций используется
именно дробь (числитель и знаменатель в копейках), а не округлённый
процент. Для отображения она округляется до 0,1 %:
`roundDiv(receiptDiscountTotal * 1000, receiptAmount)` промилле.
Если `receiptAmount = 0`, процент не определён (`null`, в UI `—`), а скидка,
приходящаяся на операцию, равна 0.

## 5. Деньги, проценты и округление

- Расчёты ведутся в `BigInt`. Результаты (всегда много меньше 2^53)
  приводятся к `number`. Суммы по закупке/категориям складываются как
  `number`.
- **Максимум суммы:** `MAX_AMOUNT_KOPECKS = 9_999_999_999`
  (99 999 999,99 ₽). Относится к сумме чека, сумме операции, возврату и
  фиксированным скидкам.
- Округление математическое (half away from zero), для делителя `d > 0`:

```ts
function roundDiv(n: bigint, d: bigint): bigint {
  const neg = n < 0n
  const a = neg ? -n : n
  const q = (2n * a + d) / (2n * d)   // floor(a/d + 1/2)
  return neg ? -q : q
}
```

  Примеры: `0,5 → 1`, `−0,5 → −1`. Не использовать `Math.round`
  (`Math.round(-2.5) === -2`).
- Каждая скидка (части скидки чека, скидка операции, скидка чека,
  приходящаяся на операцию) округляется **независимо**, до копеек.
- **Ввод денег:** строка с точкой или запятой, до двух знаков после
  разделителя, пробелы-разделители допускаются. Разбор — строкой в копейки,
  без `parseFloat × 100`. Больше двух знаков — ошибка валидации.
- **Ввод процента:** до одного знака после разделителя; `12,5` → `125 ‰`.
  Больше одного знака — ошибка валидации.
- **Отображение:** суммы — `1 234,56 ₽`, проценты — `12,5 %`
  (формат `ru-RU`).

## 6. Операция: индивидуальная скидка, возврат и скидка чека

По умолчанию у операции индивидуальной скидки нет — действует только
скидка чека. Отдельный переключатель включает индивидуальную скидку;
после включения выбирается способ ввода (сумма / процент) и значение.
При выключении переключателя поле `operationDiscount` удаляется.

Порядок расчёта:

```text
base                  = amount - refund                     (refund = 0, если нет)
operationDiscount     = нет       → 0
                        amount    → введённая сумма
                        percent   → roundDiv(base * permille, 1000)
afterOperationDiscount = base - operationDiscount
receiptDiscountForOp  = receiptAmount == 0
                          ? 0
                          : roundDiv(afterOperationDiscount * receiptDiscountTotal, receiptAmount)
operationNet          = afterOperationDiscount - receiptDiscountForOp
```

Эквивалентная запись: `operationNet = (expense − refund) − скидка операции − скидка чека`.

Иными словами: сначала применяется возврат, затем скидка операции (на базе
после возврата), затем скидка чека как эффективная доля. Каждая скидка
округляется независимо.

Примеры (чек 1 000 ₽ со скидкой чека 150 ₽, т.е. 15 %):

| Операция | base | скидка операции | после неё | скидка чека | итог |
|---|---|---|---|---|---|
| 400 ₽, без скидки | 400 | 0 | 400 | 60,00 | **340,00 ₽** |
| 400 ₽, личная 10 % | 400 | 40,00 | 360 | 54,00 | **306,00 ₽** |

Расход 1 000 ₽, возврат 1 000 ₽, индивидуальной скидки нет → `base = 0`,
итог `0`. Расход 1 000 ₽, возврат 300 ₽, скидка чека 10 % → `base = 700`,
скидка чека 70 ₽, итог `630 ₽`.

### Интерпретация

Эффективный процент применяется к операциям как доля, даже если скидка чека
введена фиксированной суммой. Конкретная денежная скидка между операциями
не распределяется. Сумма чека и сумма операций независимы, поэтому сумма
скидок по операциям может отличаться от абсолютной скидки чека — это
допустимо.

### Предупреждения

Сохранение не блокируется, значения не корректируются автоматически.
Предупреждение показывается в форме операции (в момент ввода) и в списке,
если выполняется любое из условий:

- `operationNet < 0` (в том числе без возврата — например, фиксированная
  скидка больше суммы или скидка чека больше 100 %);
- `refund > expense` (возврат больше расхода).

## 7. Расчёты чека, закупки и категорий

Сверка чека (`difference`):

```text
operationsGross = sum(operation.amountKopecks)     // по операциям этого чека
difference      = receipt.amountKopecks - operationsGross
```

Сравниваются сумма чека до скидок и сумма расходов операций до скидок;
возвраты и скидки в сверке не участвуют. При `difference ≠ 0` показывается
предупреждение, сохранение не блокируется. Если у чека нет операций,
предупреждение не показывается (показывается пустое состояние).

**Карточка чека** показывает: введённую сумму до скидок; скидку (в ₽ и %,
по эффективному проценту); итог операций чека
(`sum(operationNet)`); предупреждение о расхождении, если оно есть;
комментарий.

**Закупка** (шапка экрана и карточка в списке) — только по операциям:

```text
purchaseGross    = sum(operation.amount - operation.refund)   // брутто за вычетом возвратов
purchaseNet      = sum(operationNet)                          // со скидками
purchaseDiscount = purchaseGross - purchaseNet
purchaseRate     = roundDiv(purchaseDiscount * 1000, purchaseGross) ‰ | null (purchaseGross = 0)
```

В закупке также может показываться сумма возвратов
`sum(refund)`.

**Категория:** `categoryNet = sum(operationNet)` и
`categoryGross = sum(amount - refund)` по операциям закупки с этой
категорией (в списке категорий — по всем операциям, если такой экран
понадобится).

Чек без операций и чек с суммой, не совпадающей с суммой операций, на
итоги закупки не влияют.

## 8. Категории

Страница управления категориями (маршрут `/categories`):

- список активных категорий, сортировка по названию по алфавиту
  (`localeCompare('ru')`) сверху вниз;
- переключатель «Показывать архивные»: архивные отображаются в том же
  списке (в алфавитном порядке), приглушённо;
- создание категории;
- редактирование названия и необязательного комментария;
- архивирование категории и возврат из архива.

Правила:

- Название обязательно (после `trim` не пусто).
- Название уникально без учёта регистра, после `trim`, среди **всех**
  категорий, включая архивные (при создании и переименовании).
- Архивная категория остаётся связанной со старыми операциями и
  отображается у них; для новых операций не предлагается.
- В форме операции выбор для нового значения — только из активных
  категорий. Если редактируемая операция ссылается на архивную категорию,
  она отображается как прежнее значение и остаётся у операции, пока
  пользователь явно не выберет активную категорию.
- Физическое удаление категорий в пользовательском сценарии не
  предусмотрено.

## 9. Экран списка закупок

Маршрут `/`.

- Заголовок «Закупки» и кнопка `+`.
- Карточки от новых к старым: `date DESC`, при равных датах `createdAt DESC`.
- Карточка: название, дата (`dd.mm.yyyy`), сумма (`purchaseGross`),
  итог со скидками (`purchaseNet`) и скидка (`purchaseDiscount`).
- Создание закупки: дата = **локальная** сегодняшняя дата (не через
  `toISOString`, чтобы не получить вчерашнюю дату около полуночи), название
  `Закупка от dd.mm.yyyy`.
- Нажатие на карточку открывает закупку.

## 10. Экран закупки

Маршрут `/purchases/[purchaseId]`.

Вверху: название, дата, сводные суммы (`purchaseGross`, `purchaseNet`,
`purchaseDiscount` и процент). Переключатель представления:

- **Чеки** — карточки чеков с введёнными суммами и скидками. Тап по
  карточке открывает экран чека `/purchases/[purchaseId]/receipts/[receiptId]`,
  где находятся операции этого чека (добавление, правка, удаление).
- **Категории** — категории с операциями закупки (группы по алфавиту,
  включая архивные): для каждой показаны расходы и итого; сами операции в
  этом представлении не отображаются.

Это два представления одного набора данных; изменения операций сразу
отражаются в итогах обоих.

Действия «изменить», «удалить», «в архив» доступны через меню «⋯» на
карточках. Со страницы категорий, открытой из закупки, есть кнопка «Назад»
к этой закупке.

Порядок: чеки и операции внутри чека — по `createdAt` (по возрастанию, при
равенстве — порядок вставки); операции внутри группы категории — по
`createdAt`.

Действия: добавить чек; открыть и редактировать чек; открыть чек; добавить операцию в
чек (на экране чека); редактировать и удалять операцию (там же); перейти на страницу категорий.

Название и дата закупки редактируются без отдельного экрана (модальное
окно). Название обязательно (не пусто после `trim`).

**Дата закупки:**

- Нативный `<input type="date">`; значение хранится как `yyyy-mm-dd`,
  отображается как `dd.mm.yyyy` (форматировать строкой, без `Date`, чтобы
  не сдвинуть день часовым поясом).
- Дата обязательна. Нативный ввод не даёт выбрать несуществующую дату, но
  поле можно очистить, а в некоторых браузерах оно может деградировать до
  текстового, поэтому при сохранении всё равно проверяется непустое и
  реальная календарная дата (`yyyy-mm-dd`).
- При смене даты название обновляется автоматически, если оно равно
  автоназванию прежней даты (`Закупка от <старая дата>`); вручную
  изменённое название не трогается.

## 11. Карточка и форма чека

Форма:

- сумма до скидок;
- первая скидка: сумма или процент (по умолчанию сумма = 0 — это и есть
  «без скидки»);
- кнопка «Добавить вторую скидку» (и «Убрать вторую скидку»);
- для второй скидки: сумма или процент; если процент — выбор базы:
  исходная сумма / после первой скидки;
- комментарий;
- отмена / сохранение.

Подсказки в форме (не сохраняются):

- в режиме суммы показывается эквивалентный процент (от соответствующей
  базы, с точностью 0,1 %);
- в режиме процента показывается получившаяся сумма в ₽;
- при переключении режима в поле подставляется эквивалентное значение
  (процент округляется до 0,1 %).

Скидка больше 100 % допустима. Сохраняется выбранный режим ввода
и одно значение.

## 12. Карточка и форма операции

Форма операции:

- сумма расхода до скидок;
- обязательная категория (активные);
- комментарий (необязательно);
- переключатель индивидуальной скидки (по умолчанию выключен): способ
  ввода сумма/процент и значение;
- переключатель «Возврат» (по умолчанию выключен): при включении поле
  суммы предзаполняется суммой расхода; сумма редактируется;
- если у редактируемой операции выбрана архивная категория, она отображается
  как прежнее значение и сохраняется, пока пользователь явно не выберет
  активную категорию; для новой операции архивная категория недоступна;
- в форме показывается итог операции и предупреждения (раздел 6).

Карточка операции: категория (архивная — приглушённо), расход, возврат (если
есть), итог операции, предупреждение при необходимости, комментарий.

## 13. Валидация

| Поле | Правило |
|---|---|
| Название закупки | не пусто после `trim` |
| Дата закупки | непустая, реальная календарная дата |
| Сумма чека, сумма операции | целое число копеек, `> 0`, `≤ MAX_AMOUNT_KOPECKS` |
| Фиксированная скидка (чека, операции) | `≥ 0`, `≤ MAX_AMOUNT_KOPECKS`; `0` допустим |
| Процентная скидка | `≥ 0`, шаг 0,1 %, технический предел 1000,0 % |
| Возврат | если указан — `> 0`, `≤ MAX_AMOUNT_KOPECKS`; «нет возврата» = поле отсутствует |
| Отрицательные значения | недопустимы везде (скидка-наценка не поддерживается) |
| Категория операции | обязательна и активна на момент сохранения |
| Название категории | не пусто, уникально (раздел 8) |

Не блокируют сохранение (только предупреждения): отрицательный итог операции,
возврат больше расхода, расхождение суммы чека и операций, скидка больше
100 %.

## 14. Хранилище (сейчас: `localStorage`)

Все данные лежат под одним ключом `purchase-tracker:data` в одном
JSON-документе (запись атомарна, каскадное удаление не может оставить
«висячих» ссылок):

```ts
interface StorageDocument {
  schemaVersion: 1
  purchases: Purchase[]
  receipts: Receipt[]
  operations: Operation[]
  categories: Category[]
}
```

- Доступ к данным — через репозиторий с **асинхронным интерфейсом**
  (методы возвращают `Promise`), чтобы замена на IndexedDB не требовала
  переписывать UI. Все CRUD работают с этой моделью напрямую.
- Репозиторий загружает документ в память, мутации применяются к нему и
  сохраняются целиком (`JSON.stringify` → `setItem`). Ошибка записи
  (например, `QuotaExceededError`) показывается пользователю и не
  скрывается.
- Каскады: удаление закупки удаляет её чеки и их операции; удаление чека
  удаляет его операции; удаление операции затрагивает только её.
  Категории при этом сохраняются.
- **Ошибки загрузки:** если JSON не парсится, структура неверна или
  `schemaVersion` неизвестна — выводится `alert` с описанием ошибки, а
  приложение **не записывает** ничего в хранилище (чтобы не затереть
  данные) до исправления. Рекомендуется дать в этом состоянии скачать
  сырое значение ключа.
- Синхронизация вкладок: по событию `storage` для ключа данных документ
  перечитывается.
- Миграция данных из прежних отдельных ключей `localStorage` не требуется:
  данных для переноса нет. Если `purchase-tracker:data` отсутствует,
  приложение начинает с пустого документа; legacy-ключи не читаются.
- Старая экспериментальная схема IndexedDB (`purchase-tracker`, stores
  `groups`/`groupItems`) не используется и не мигрируется; при желании
  удаляется вручную.
- **Выгрузка JSON:** на странице «Разное» кнопка выгружает весь документ
  (`StorageDocument` + `exportedAt`) файлом `purchase-tracker-yyyy-mm-dd.json`.
  Импорта в этой версии нет.

## 15. Целевое хранилище (позже: IndexedDB)

Миграция `localStorage → IndexedDB` — отдельная будущая задача, и она
должна **сохранять данные** (в отличие от удалённой миграции v1→v2).
Ориентир:

- БД `purchase-tracker`; stores и индексы:
  - `purchases` (keyPath `id`, индекс `date`);
  - `receipts` (keyPath `id`, индекс `purchaseId`);
  - `operations` (keyPath `id`, индексы `receiptId`, `categoryId`);
  - `categories` (keyPath `id`; архивные хранить как `archived: 0|1`
    или фильтровать в памяти — boolean не является допустимым ключом
    IndexedDB, записи не попадут в индекс по `archived`).
- Версию БД задать явно; при встрече более новой/неизвестной версии —
  ошибка по тому же сценарию, что в разделе 14.
- При миграции можно добавить в `Operation` денормализованный
  `purchaseId`, если понадобится быстро выбирать операции закупки.
- Порядок миграции: прочитать документ, проверить `schemaVersion`, записать
  всё в IndexedDB одной транзакцией, поставить флаг «мигрировано», старый
  ключ `localStorage` не удалять до подтверждения.

calculateReceiptEffectiveRate(receipt): { numerator: Kopecks; denominator: Kopecks } | null
formatEffectivePermille(receipt): Permille | null      // для отображения
calculateOperationDiscount(operation, base): Kopecks

## 17. Обязательные тест-кейсы

Суммы в копейках, если не указано иное.

Скидки чека:

1. Чек без скидки (одна часть `amount = 0`).
2. Одна скидка в процентах.
3. Одна фиксированная скидка и корректная эффективная дробь.
4. Две скидки: вторая процентная от исходной суммы (5 000 ₽, 10 % + 5 % → 750 ₽).
5. Две скидки: вторая процентная от суммы после первой (→ 725 ₽).
6. Вторая скидка фиксированной суммой.
7. Скидка больше 100 % (чек 1 000 ₽, скидка 1 200 ₽, операция 500 ₽ → скидка
   чека 600 ₽, итог −100 ₽, предупреждение).
8. `receiptAmount = 0`: эффективный процент `null`, скидка операции = 0.

Операции:

9. Без индивидуальной скидки: применяется доля скидки чека (400 ₽, чек 15 % → 340 ₽).
10. Индивидуальная процентная скидка применяется до скидки чека (400 ₽, 10 %
    → 306 ₽).
11. Индивидуальная скидка фиксированной суммой.
12. Расход 1 000 ₽, возврат 1 000 ₽, скидки нет: база и итог 0.
13. Частичный возврат (1 000 ₽, возврат 300 ₽, скидка чека 10 % → 630 ₽).
14. Возврат больше расхода: предупреждение, автоограничения нет.
15. Фиксированная индивидуальная скидка при полном возврате (база 0, скидка
    500 ₽, скидка чека 10 % → итог −450 ₽, предупреждение).
16. Итог < 0 без возврата показывает предупреждение.

Округление:

17. Каждая скидка округляется независимо (чек 300 ₽, фикс. скидка 10 ₽, три
    операции по 100 ₽ → скидка чека на каждую 3,33 ₽; сумма 9,99 ≠ 10).
18. Half away from zero: `0,5 → 1`, `−0,5 → −1`.
19. Большие значения (`MAX_AMOUNT_KOPECKS` × `MAX_AMOUNT_KOPECKS`) не теряют
    точность (BigInt).

Сверка и итоги:

20. Сумма чека сравнивается с суммой операций до скидок; возвраты не
    участвуют.
21. Сумма чека и операций различается: предупреждение, сохранение разрешено.
22. Чек без операций: предупреждения о расхождении нет, на итоги закупки не
    влияет.
23. `purchaseGross` = сумма `amount − refund`; `purchaseNet` = сумма итогов
    операций; `purchaseDiscount` = разность.
24. Итог категории = сумма итогов её операций.

Ввод и валидация:

25. Разбор денег: `1 234,5 → 123450`, `0,001` — ошибка, `0` для суммы — ошибка.
26. Разбор процента: `12,5 → 125`, `12,55` — ошибка, отрицательные — ошибка.
27. Сумма выше `MAX_AMOUNT_KOPECKS` не принимается.
28. Дата: пустая и несуществующая отклоняются; хранится `yyyy-mm-dd`; сегодняшняя
    дата берётся локальная.
29. Автоназвание обновляется при смене даты только если название не менялось
    вручную.

Категории:

30. Архивная категория остаётся видимой у старых операций и не
    предлагается новым.
31. Операцию нельзя сохранить без активной категории.
32. Дубликаты категорий (регистр, пробелы, архивные) не создаются и не
    переименовываются в дубликат.
33. Возврат из архива работает; архивные скрываются/показываются
    переключателем и приглушены.

Представления и хранилище:

34. Операции чека на экране чека и итоги категорий в закупке строятся из
    одних данных; правка операции сразу меняет итоги в обоих местах.
35. Каскадное удаление (закупка → чеки → операции; чек → операции);
    категории сохраняются.
36. Порядок: закупки `date DESC, createdAt DESC`; чеки и операции по `createdAt`;
    категории по алфавиту.
37. Повреждённый JSON / неизвестная `schemaVersion`: `alert`, записи в
    хранилище нет.
38. Событие `storage` перечитывает данные.

## 18. Допущения по умолчанию

Не подтверждались явно — при желании поменять:

- Формы чека и операции — модальные окна/нижние листы (shadcn-svelte
  Dialog/Drawer) на экране закупки, а не отдельные маршруты.
- Технический предел процента — 1000,0 % (10 000 ‰).
- Лимиты длины: название — 100 символов, комментарий — 500.
- Для чека без операций предупреждение о расхождении не показывается.
- Подтверждение удаления показывает число каскадно удаляемых сущностей.
- Для архивирования категории подтверждение не требуется.

## 19. SvelteKit, PWA и хостинг

- `@sveltejs/adapter-static` с `fallback` (имя файла, напр. `200.html` или
  `index.html`); в корневом `+layout.ts`:
  `export const ssr = false; export const prerender = false`
  (`localStorage` и IndexedDB есть только в браузере).
- Маршруты: `/`, `/purchases/[purchaseId]`, `/categories`, страница
  «Разное» (уже существует).
- `kit.paths.base` брать из переменной окружения (`BASE_PATH`); если
  приложение лежит не в корне домена (например, GitHub Pages
  `/<repo>/`), `base` должен совпадать с `manifest.start_url`, `manifest.scope`
  и `base`/`scope` service worker.
- Workbox `navigateFallback` должен указывать на тот же файл, что и
  `fallback` адаптера, чтобы deep link `/purchases/<id>` работал офлайн.
- На GitHub Pages как fallback обычно нужен `404.html`.
- Рекомендуется запрашивать `navigator.storage.persist()`: экспорт пока
  ручной, а данные существуют только в браузере.

## 20. Не входит в v3

- Backend, аккаунты, синхронизация.
- Фотографии чеков и OCR.
- Импорт (экспорт JSON входит, см. раздел 14).
- Поиск, фильтрация, аналитические графики.
- Сложные жесты и drag & drop.
- Автоматическое распределение фиксированной скидки чека по операциям.
- Автоматическое исправление случаев, когда возврат превышает расход.
- Миграция старой экспериментальной схемы IndexedDB; миграция
  `localStorage → IndexedDB` выполняется позже отдельной задачей.

## 21. Принципы

- Чек хранит сумму до скидок и задаёт скидку для операций через точную
  эффективную дробь; сам итоги закупки не определяет.
- Итоги закупки и категорий считаются по операциям.
- Возврат вводится в брутто-шкале и вычитается из суммы операции до
  расчёта скидок.
- Индивидуальная скидка операции применяется после возврата и до скидки
  чека.
- Категория обязательна для операции; архивирование сохраняет историю.
- Сумма чека и сумма операций независимы; несовпадение — предупреждение.
- Отрицательные итоги и возвраты больше расхода — предупреждение, без
  автоматической коррекции.
- Деньги — копейки, проценты — промилле, расчёты — `BigInt`.
